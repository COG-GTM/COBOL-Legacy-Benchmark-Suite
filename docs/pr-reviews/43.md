# PR Review Log #43

## PR: feat: Migrate COBOL Legacy Benchmark Suite to Java/Spring Boot

**Reviewed by:** Devin (on behalf of Daniella Grimberg)

## Summary
- **Scope**: Full COBOL-to-Java/Spring Boot migration of an Investment Portfolio Management System (Phases 1-4). Backend (entities, services, controllers, security, batch) + React/Vite frontend. ~10,800 lines added across 86 files.
- **Risk**: **High** -- touches authentication, financial transaction processing, and position accounting with several correctness and security gaps.
- **Positives**:
  - Well-structured layered architecture (controller -> service -> repository) following Spring Boot conventions.
  - COBOL return code semantics (0/4/8/12) faithfully mapped to Java.
  - Clean domain model with proper JPA annotations and composite keys.
  - Good use of Spring Batch for history loading, Spring Security + JWT for auth.
  - Frontend is clean, uses shadcn/ui components consistently, and has proper routing.
  - Thorough PR description with screenshots and testing instructions.
- **Concerns** (see inline comments on PR for details):
  1. **[blocker]** JWT secret hardcoded in `application.yml` -- anyone with repo access can forge tokens.
  2. **[blocker]** CORS allows all origins (`*`) -- cross-origin attacks possible.
  3. **[blocker]** H2 console open to unauthenticated users with frame-options disabled -- full DB access.
  4. **[blocker]** `/api/auth/register` is publicly accessible -- unlimited account creation.
  5. **[major]** Actuator endpoints fully open -- can leak env vars, heap dumps.
  6. **[major]** Login error leaks Spring Security exception messages (user enumeration).
  7. **[major]** Generic exception handler exposes internal error details to clients.
  8. **[major]** `processBuyTransaction` uses `LocalDate.now()` in composite key lookup -- will create duplicate position rows instead of updating existing positions.
  9. **[major]** `processSellTransaction` doesn't guard against negative quantity.
  10. **[major]** `processFeeTransaction` doesn't guard against negative cash balance.
  11. **[major]** `POST /api/transactions` bypasses validation entirely.
  12. **[minor]** Batch reader fetches data at bean creation, not at job execution.
  13. **[minor]** No pagination on `GET /api/portfolios` and `GET /api/transactions`.
  14. **[minor]** `DataInitializer` with weak passwords not gated behind a dev profile.
  15. **[minor]** Frontend doesn't validate token expiry on restore from localStorage.
  16. No automated tests included (acknowledged in PR description).

## Decision
**Request changes.**

The security issues (items 1-4) and the position-update correctness bug (item 8) must be resolved before this can be merged. The financial integrity issues (items 9-11) are also strongly recommended.

## Next steps
1. Externalize JWT secret via environment variable; remove hardcoded value from YAML.
2. Restrict CORS to known frontend origin(s); make configurable.
3. Gate H2 console and `DataInitializer` behind `@Profile("dev")`.
4. Remove or protect the public register endpoint.
5. Restrict actuator to health/info only, or require authentication.
6. Fix `processBuyTransaction` to look up existing positions by `portfolioId + investmentId` (ignoring date).
7. Add negative-balance guards in sell and fee processing.
8. Enforce validation on `POST /api/transactions` or remove the unvalidated endpoint.
9. Sanitize error messages returned to clients (login, generic handler).
10. Add `@StepScope` to the batch reader so it queries at execution time.
11. Add unit/integration tests for critical business logic (transaction validation, position updates).
