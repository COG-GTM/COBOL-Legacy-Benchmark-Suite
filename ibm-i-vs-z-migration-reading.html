IBM i vs. IBM z, and How Banks Migrate Off Them

A reading module for banking-technology teams. It explains the two dominant IBM platforms that still run core banking — the midrange IBM i (AS/400) and the mainframe IBM z (z/OS) — and the mainstream strategies for modernizing off them while preserving full banking functionality. Examples are grounded in a real COBOL codebase, the Investment Portfolio Management System from the COBOL‑Legacy‑Benchmark‑Suite.

01 Why a bank cares about IBM i and IBM z

The "system of record" for accounts, balances and ledgers at most established banks still lives on an IBM platform. Understanding these platforms is the starting point for any credible modernization program.

Roughly speaking, when a bank runs core software on IBM hardware it is on one of two families:

  • IBM i — the midrange platform descended from the AS/400. Extremely common for regional banks, credit unions and community banks. The widely deployed Jack Henry SilverLake (formerly Silverlake Axis) core banking system runs on IBM i.
  • IBM z — the mainframe (z/OS). The backbone of large "money-center" banks, card networks and clearing/settlement, where transaction volumes and availability requirements are extreme.

What "maintaining full functionality" means for core banking

A core banking migration is not a website rewrite. If a single ledger entry is lost or double-posted, real money and regulatory standing are at stake. "Full functionality" is a demanding checklist:

  • Accounts & ledgers — the authoritative record of balances and postings; must always foot.
  • Batch settlement — overnight cycles: interest accrual, position updates, clearing, statementing.
  • Regulatory reporting — scheduled, auditable extracts (e.g. positions, holdings, exposures).
  • 24×7 availability — digital and card channels never sleep; the shrinking batch window must not cause outages.
  • ACID transactions — Atomic, Consistent, Isolated, Durable posting is non-negotiable.
  • Audit trail — who changed what, when; immutable history for examiners.
Grounded in the benchmark repo

The reference system exhibits every one of these traits. Its DB2 schema (src/database/db2/db2-definitions.sql) defines PORTFOLIO_MASTER, INVESTMENT_POSITIONS and TRANSACTION_HISTORY with foreign keys and LAST_MAINT_DATE/LAST_MAINT_USER audit columns on every table — exactly the "who/when" trail examiners expect. Overnight batch settlement appears as JCL such as src/jcl/batch/RPTPOS.jcl (a daily position report), and ACID behavior is centralized in DB2CMT, a commit controller issuing COMMIT WORK, ROLLBACK WORK and SAVEPOINT.

02 IBM i (AS/400), explained from scratch

IBM i is best understood as an integrated, database-centric operating system: the OS, the relational database and the security model are one product, not a stack you assemble.

A short lineage

  1978            1988             2000            2008 → today
   |               |                |                |
System/38  →   AS/400    →    iSeries   →   IBM i  (on IBM Power servers)
(capability   (unified       (rebrand,        (current name; OS releases
 architecture, midrange       eServer line)    7.3 / 7.4 / 7.5)
 single-level  business
 storage)      system)

The same architectural ideas from System/38 survive today. Programs written for the AS/400 in the late 1980s frequently still run on modern IBM i with little or no change — a deliberate compatibility promise that is a big reason banks stayed.

Defining characteristics

  • Integrated OS + Db2 for i — the database is built into the operating system. There is no separate "install the database" step; every file is effectively a database object.
  • Single-level storage — main memory and disk are treated as one enormous flat address space. Applications don't manage where data physically lives; the OS pages it transparently.
  • Object-based architecture — everything (programs *PGM, files *FILE, data areas, user profiles) is a typed object with an owner and authorities. You cannot treat a program as raw bytes; the system enforces object integrity.
  • DDS physical & logical files — classic data definition uses DDS. A physical file (PF) holds the actual records; a logical file (LF) is a view/index/join over one or more PFs. (Modern IBM i also supports plain SQL DDL.)
  • Language mix — RPG is the signature language (RPG III / ILE RPG / free-format RPG), alongside COBOL/400 and CL (Control Language) for scripting and job control.
  • 5250 "green screen" — character terminals (and emulators) speaking the 5250 data stream. Menu-driven, keyboard-first data entry.
  • Journaling & commitment control — the native recovery model. Journaling records every change to a file; commitment control groups changes into ACID transactions that can be committed or rolled back — conceptually the IBM i counterpart to database transaction logs.
IBM i in banking Jack Henry's SilverLake core banking platform (originating from Silverlake Axis) runs on IBM i and powers a large share of US community and mid-tier banks. If a bank says "we run on the AS/400", they almost certainly mean IBM i.
Reading the benchmark on IBM i terms

The benchmark is written for z/OS, but many patterns translate to IBM i concepts. Its indexed PORTMSTR VSAM file (keyed master, src/database/vsam/vsam-definitions.txt) maps naturally to an IBM i keyed physical file; the DB2 SAVEPOINT / COMMIT WORK logic in DB2CMT is the direct analogue of IBM i commitment control; and the checkpoint/restart program CKPRST resembles the kind of recovery scaffolding that IBM i journaling provides more natively.

03 IBM z (z/OS), explained from scratch

IBM z is the mainframe. Where IBM i integrates everything into one product, z/OS is a layered stack of specialized subsystems, each best-of-breed for scale, throughput and availability.

Lineage in one line

  System/360 (1964) → System/370 → System/390 → zSeries → IBM Z (z/Architecture, 64-bit)
       the original                                          current mainframes running z/OS
       "mainframe"                                           (plus z/VM, Linux on Z, z/VSE)

The z/OS subsystem stack

  • z/OS — the operating system that schedules work, manages storage and runs subsystems.
  • CICS (Customer Information Control System) — the online transaction monitor. It hosts thousands of concurrent terminal/API transactions with tiny, fast programs. The dominant pattern is pseudo-conversational: a program sends a screen and ends, freeing resources; the next keystroke starts a fresh transaction that picks up saved state.
  • Db2 for z/OS — the relational database, tuned for enormous concurrency and data volumes.
  • VSAM (Virtual Storage Access Method) — high-performance record files. KSDS (Key-Sequenced Data Set) is the keyed/indexed flavor used for master and history files.
  • JCL (Job Control Language) — how batch work is described: which program to run, which datasets (DD statements) to allocate, and in what order (job steps).
  • Languages — COBOL dominates business logic, with PL/I and low-level HLASM (High Level Assembler) for performance-critical or system code.
  • 3270 "green screen" — the mainframe terminal. Screens are defined with BMS (Basic Mapping Support) maps that lay out fields on a 24×80 character grid.
  • Parallel Sysplex — the availability model: multiple z/OS images clustered with a shared coupling facility so the "system" survives the loss of any one machine — enabling near-continuous uptime.
Every one of these appears in the benchmark

CICS + pseudo-conversational: src/programs/online/INQPORT.cbl issues EXEC CICS READ FILE('POSFILE'), EXEC CICS SEND MAP('POSMAP') MAPSET('INQSET'), then EXEC CICS RETURN — a textbook send-and-end handler. BMS 3270 maps: src/maps/INQSET.bms defines DFHMDI ... SIZE=(24,80) screens with PF-key legends (PF3=Exit PF7=Previous PF8=Next). VSAM KSDS: PORTMSTR is ORGANIZATION: KSDS, KEY LENGTH: 12, defined via IDCAMS DEFINE CLUSTER. JCL batch: RPTPOS.jcl shows //STEP01 EXEC PGM=RPTPOS00 with STEPLIB/DD dataset allocations. Db2 for z/OS: the schema and the DB2CMT commit controller (the program even declares SOURCE-COMPUTER. IBM-ZOS).

Both are IBM, both run COBOL, both have "green screens" — but their philosophies differ. IBM i favors integration and simplicity; IBM z favors specialized subsystems at extreme scale.

On IBM z each concern is a distinct, individually-tuned subsystem — more parts to run, but each scales enormously.

The one-sentence contrast IBM i gives you fewer things to manage because the database is the OS; IBM z gives you more things to manage because each subsystem (CICS, Db2, VSAM) is separately engineered for the largest possible scale and availability.

05 Migration options — the 6 R's

"Getting off" IBM i or IBM z is not one decision. The industry frames the choices as the 6 R's. A large bank rarely picks one — it assigns a strategy per application domain.

R — (a) Rehost

Lift-and-shift / emulation

Recompile the COBOL essentially unchanged and run it on Linux/x86 (or cloud) under an emulation runtime — e.g. Micro Focus, GnuCOBOL, or a CICS/JCL emulator.

Pros: fastest, lowest logic risk; frees expensive MIPS/hardware.

Cons: you keep the old design and COBOL; limited modernization; emulator licensing/fidelity.

Risk: Low
R — (b) Replatform

Keep logic, modernize data

Retain the application logic but move the data layer to a modern RDBMS (e.g. VSAM/Db2 → PostgreSQL, Db2 LUW, Oracle) and/or a supported COBOL runtime.

Pros: unlocks modern data tooling/analytics; moderate effort.

Cons: data access rewrites (EXEC SQL/CICS file I/O); careful data-type mapping (packed decimal!).

Risk: Medium
R — (c) Refactor

Automated code transformation

Convert COBOL to Java or C# via automated transformation tools (and, increasingly, LLM-assisted translation — the very purpose of this benchmark suite).

Pros: exits COBOL skills scarcity; modern language & CI/CD.

Cons: machine-translated code can be unidiomatic ("JOBOL"); needs heavy testing & equivalence proof.

Risk: Medium
R — (d) Rearchitect

Cloud-native microservices

Redesign around bounded domains as microservices/event-driven services on the cloud, replacing monolithic batch + CICS patterns.

Pros: elastic scale, independent deploys, best long-term agility.

Cons: highest cost/time; must re-derive decades of embedded business rules; distributed-systems complexity.

Risk: High
R — (e) Replace

Buy a COTS core banking package

Retire the custom system and adopt a packaged core (e.g. Temenos, Finacle, Thought Machine, Mambu, or a JH product).

Pros: vendor-maintained, roadmap & compliance built in.

Cons: fit-gap pain; lose bespoke differentiators; big-bang risk; data migration is enormous.

Risk: High
R — (f) Retain / Encapsulate

Wrap behind APIs (strangler fig)

Deliberately keep the legacy running and expose it through APIs, peeling off functionality incrementally — the strangler fig pattern.

Pros: immediate integration value; de-risks by slicing; no forced rewrite.

Cons: legacy debt persists; needs disciplined routing/anti-corruption layer.

Risk: Low–Med
Mapped onto the benchmark code
  • Rehost: take RPTPOS00 and its RPTPOS.jcl and recompile under GnuCOBOL/Micro Focus with a JCL emulator — same logic, x86 host.
  • Replatform: repoint INQPORT's EXEC CICS READ FILE('POSFILE') and the DB2 schema onto PostgreSQL; the tricky part is mapping COMP-3 packed decimals and DECIMAL(18,4) money fields losslessly.
  • Refactor: translate DB2CMT's COMMIT/ROLLBACK/SAVEPOINT logic into a Java transaction service — the kind of pair this suite exists to benchmark.
  • Rearchitect: split "positions", "transactions" and "reporting" (today one VSAM/Db2 monolith) into separate services around the PORTFOLIO_MASTER / INVESTMENT_POSITIONS / TRANSACTION_HISTORY domains.
  • Encapsulate: put a REST facade in front of the CICS INQPORT inquiry so channels call an API instead of a 3270 screen — strangler entry point.

06 A canonical, phased migration framework

The detailed recommended path is produced separately; what follows is a solid, general framework that works regardless of which R's you choose. In banking, every phase is governed by risk controls.

1

Assess & discover

Build a full inventory: programs, copybooks, JCL, CICS transactions, VSAM/Db2 objects, batch schedules, and their dependencies. Establish which code is dead, which is hot, and where the business rules actually live. Deliverable: application portfolio + dependency map + risk/complexity heatmap.

2

Establish target architecture & guardrails

Decide target runtime(s), data platform, integration standards, security/compliance controls, and the per-domain choice of R. Define non-negotiable guardrails (data integrity, auditability, latency SLOs).

3

Decompose into domains / services

Slice the monolith along business boundaries (accounts, positions, transactions, reporting). Identify seams where an anti-corruption layer can isolate new code from legacy formats (e.g. packed-decimal).

4

Data migration strategy

Plan the movement of master and history data: schema mapping, code-page/EBCDIC conversion, packed-decimal fidelity, referential integrity, and a repeatable, reversible load. Decide on one-time vs. continuous replication (change data capture) during coexistence.

5

Incremental migration (strangler) with parallel run & reconciliation

Migrate a domain at a time behind a routing facade. Run old and new in parallel and reconcile outputs (balances, ledgers, report totals) until they match to the penny before trusting the new path. Never big-bang the ledger.

6

Cutover & decommission

Once reconciliation is clean and regulators have signed off, cut traffic to the new system, keep the legacy as a hot fallback for a defined window, then decommission and archive per retention rules.

Why the risk band spans every phase In core banking the migration mechanics are the easy part; proving equivalence is the hard part. Dual-run reconciliation, penny-level balancing, regulatory sign-off and a tested rollback are what let a bank move without a reportable incident. The reference system's per-table audit columns and its DB2CMT commit/rollback discipline are exactly the hooks you lean on to prove that equivalence.
